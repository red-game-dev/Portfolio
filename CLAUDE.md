# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Single-page personal portfolio (Redeemer Pace) built on Next.js **Pages Router**, deployed to Vercel at <https://redgame.dev>. One route (`src/pages/index.tsx`) renders every section; navigation is anchor-based scrolling, not routing.

## Commands

```bash
npm run dev                                  # dev server (localhost:3000), webpack not Turbopack
npm run build && npm start                   # production build / serve
npm run lint                                 # eslint --fix over src/ and __tests__/src/
npm run lint:check                           # the same without --fix, failing on any warning (what CI runs)
npx tsc --noEmit                             # typecheck (there is no script for it)
npm test                                     # jest --watch
npm run test:ci                              # every suite once
npm run test:coverage                        # once, with coverage of src/ (data excluded)
npx jest __tests__/src/pages/index.test.tsx --watchAll=false   # single test file
npx jest -t "renders every section" --watchAll=false           # single test by name
ANALYZE=true npm run build                   # bundle analysis (@next/bundle-analyzer, does not auto-open)
npm run timelapse                            # rewrite the repo time-lapse's history from git (commit the JSON)
npm run email:portrait                       # rewrite the portrait the emails reveal, from the profile picture (commit the JSON)
HUD_LAB_URL=<deployment> PLAYWRIGHT_CHANNEL=chrome npm run test:hud   # the HUD overlap check against a deployment
```

Icons are the free Font Awesome set (`@fortawesome/free-solid-svg-icons`, `free-brands`), installed from the public npm registry with no token. The committed project `.npmrc` points the `@fortawesome` scope at registry.npmjs.org, overriding any global `~/.npmrc` that still routes it to the Pro registry; it must never hold a token, since this repo is public. The few icons the free set lacks (castle, candlestick chart, treasure chest) are drawn in `src/config/icons.ts` on Font Awesome's 512 unit grid.

Use Node 22+ (`.nvmrc` pins 22.6.0, `engines` allows `22.x || 24.x`). Node 23 is not a Vercel target and triggers an `Exit handler never called!` bug in npm 10.9 that aborts installs midway and leaves `node_modules` corrupt; `rm -rf node_modules` and reinstall on 22/24 to recover. Run `nvm use` before any npm command; the global default here is 23.

Without `node_modules`, `npx tsc` and `npx eslint` do not fail cleanly: npx downloads the wrong packages instead (`tsc@2` is an unrelated squatter, and ESLint 9 rejects the legacy `.eslintrc.json`). Install first. `npm run lint` calls ESLint 8 directly because Next 16 removed `next lint`.

## Verifying changes

Every pull request and push to main runs `.github/workflows/ci.yml`: `npm run lint:check`, the typecheck and the whole Jest suite, needing no secrets (the live evals skip themselves).

**Verify against the deployed Vercel preview using the Playwright MCP tools, not a local dev server or local build.** Push the branch, let the preview deploy, then drive Playwright against the preview URL and read its console. Local runs are slow, crash-prone on this machine, and do not reflect what actually ships.

**Both `dev` and `build` pass `--webpack`.** Next 16 defaults to Turbopack, which cannot run Babel macros, and twin.macro is a Babel macro. Dropping the flag breaks every `tw` template literal. This is also why `next/font` is unusable here, so Roboto stays an external stylesheet.

`next dev` and `next build` share `.next`, and a dev server started over a production build dies with `ENOENT: .next/fallback-build-manifest.json`. If you do run locally, `rm -rf .next` between the two.

`.playwright-mcp/` holds console logs and page snapshots from those runs and is gitignored.

The voyage's HUD has a layout check of its own in a real browser, since jsdom does no layout: `/hud-lab/` (noindex, linked from nowhere) holds the HUD still with every panel it can show at once (`labVoyage` in `Finale/Voyage/lab`, handed to `VoyageDialog` as its `source` in place of the live game; `?moment=` one of `LAB_MOMENTS`: flight or descent, or what lies over the HUD or takes its place, the ready, pause and end cards, a perk's choice, the hangar, a port's trade, photo mode and the map; `&hud=full|compact`), and `e2e/hud.spec.ts` (Playwright, `playwright.config.ts`) measures what each `[data-hud-area]` paints at twelve screen sizes and fails on two panels that overlap or one that leaves the screen. What lies over the HUD is marked `data-hud-surface` (a card, a drawer, a bar) and held to its own rules: it stays on the screen, but for a card taller than it that fits across, scrolls in its overlay and keeps its actions (`data-card-actions`) in view; a card never covers the HUD's buttons; a drawer covers a panel whole or not at all. It runs in CI on every Vercel preview (`.github/workflows/hud.yml`, on `deployment_status`). `e2e/hud-known.json` would list known overlaps (none since the HUD became one grid); a new one is fixed rather than listed, and in CI an entry that no longer happens fails. Jest ignores `e2e/`.

Hydration mismatches only surface in the browser console, so they are invisible to `tsc`, ESLint, `next build` and jest. All four can be green while the page is broken at runtime. The console check is the only thing that catches them.

## Architecture

### Content is data, not markup

All site content is the `portfolioData` object exported by `src/data/resume.ts`, which only gathers one file per part of the page from `src/data/portfolio/` (`profile`, `terminal`, `sections`, `services`, `history`, `skills`, `roster`, `projects`, `caseStudies`, `game`, `domains`, `payments`, `aiUsage`, `navigation`; the view copy sits in `src/data/lens.ts`; blueprints live apart in `src/data/blueprints/` and are loaded on demand, see Blueprints). Its type, `PortfolioData`, is in `types/portfolio.d.ts`, built from the interfaces in `types/*.d.ts`; `types/` never imports data. `src/pages/index.tsx` is purely composition: it slices `portfolioData` and passes the pieces into section components. **To change what the site says, edit the matching file in `src/data/portfolio/`**. Components should stay content-free: labels, templates (`{name}` placeholders, filled by `fill()` from `packages/text/format`) and stop names are content. Skills are lists of names per `SkillGroup`; years come from the forge, never a self score. Section intros are keyed by the closed `SectionIntroKey`.

`src/components/SEO` (mounted once in `src/pages/_app.tsx`) sets the meta tags, each page's own canonical (with the trailing slash, never the home page's, or `/resume/` is folded into it) and one schema.org `@graph` per page from `createStructuredData` in `src/services/seo/structuredData.ts`, typed with `schema-dts`: the person (job title, skills, languages, employer, offers, profiles), the site, the page, and on the home page the journey breadcrumb, the recruiter FAQ and the projects, all joined by `@id` and read from `portfolioData`, so a new project or service extends it. The titles, description, FAQ and `llms.txt` labels live in `src/data/seo.ts`, composed from the content. `/llms.txt` and `/llms-full.txt` (the Ask Red knowledge without its citation keys) are rewrites in `next.config.js` to the API routes `api/llms/` and `api/llms-full/` (with the slash, and a second rule with `/en` in front, since a `locale: false` rule is matched against the path with the default locale added), which answer with plain text through `servePlainText`; `services/seo/llms.ts` pulls in the knowledge mapper, so only those routes may import it. Vercel's build adapter sometimes fails with `ENOENT ... .next/output/static/en/500.html` on a commit that then builds on a redeploy; it has happened with and without server rendered pages, so redeploy before changing code for it. `public/robots.txt` welcomes AI crawlers by name and keeps `/api/` out of every group; `public/sitemap.xml` lists the pages and the CV PDFs; a test keeps both on the canonical host and every listed path real. That host is `SITE_URL` in `src/config/site.ts` (`https://www.redgame.dev`, which the bare domain redirects to), never an environment variable: Vercel's own `HOST` variable once held the bare domain, so every canonical pointed at a redirect. The share picture is `public/images/social-card.png`, printed at 1200 by 630 with headless Chrome from the deployed `/social-card/` (noindex); print it again when the headline or the figures change. Search engines and AI crawlers read the server HTML's text, so anything that decodes from binary draws its bits with `Bits` from `DecodedText` (a `data-bits` attribute painted by CSS), never as text; the page test fails on a run of binary in the text.

### Section ids and scroll-spy

Each section renders `id={SECTION_IDS.x}` on its outer element (the shared `Section` from `src/components/Section`). **Every section id lives in `SECTION_IDS` in `src/config/sections.ts`**, lower case and in page order; a test keeps them unique. The same file holds `AUDIENCE_ANCHORS`, `ROLE_ANCHORS`, `industryAnchor()` and the hash parsers for the first screen's chips. The journey's zone boundaries are in `src/config/zones.ts`, and `index.tsx` wraps each zone's run of sections in a `Zone` (`src/components/Zone`, `display: contents`, its `data-zone` giving the run its zone's `--accent` in `globals.css`; a page test keeps each section in its own zone's run). The root's `data-zone` follows the reader for what lies outside the runs (the header, the trail, the HUD), where the accent animates across; it never restyles the sections, since animating an inherited custom property on the root restyles the whole document every frame, which froze a slow phone for seconds at each crossing. Sections that share a zone but not a subject each take a theme of their own (`Theme`, `src/components/Theme`, a `data-theme` run inside the zone's): the chain zone's Web3, Payments, More Skills by Area, What I Have Built and Code Review each have an accent (`THEME_ACCENTS` in `src/config/sectionThemes.ts`, the same values in `globals.css`, a test keeping them equal, apart from each other and from every zone's but Web3's own) and, where their content switches, a switch of their subject; the phone menu colours a stop that is one themed section in its theme. The trail (`services/journey/trail.ts`) lists every section in page order with its title. The page has a scroll padding for its fixed bars (`--bars-top` and `--bars-bottom` on `html` in `globals.css`, set by hand to the header, the zone trail and the game HUD, so they change when those bars do), which keeps a control focused by keyboard clear of them (WCAG 2.4.11); `Section` and `Anchor` cancel it with a negative scroll margin, so a jump still lands a section at the top, and `settleAtTop` counts padding plus margin. A same page link moves keyboard focus to the section it lands in (`focusLanding` in `packages/interaction/focus`, from `useSettledAnchors` and `MobileMenu`), never to the hidden anchor, and not when the link opens elsewhere.

The menus follow `JOURNEY_STOPS` in `src/config/journey.ts`: ten stops (who, offer, history, ai, web3, payments, engineering, igaming, game, beyond), each covering a run of sections from `first` to `last`, its `href` derived and its name in `menu.stops` in the content. The SEO breadcrumb is built from the same stops. A test checks the stops cover the trail end to end, so a new section only needs to sit inside a stop's run. `useJourneyNav` (called once in the header for both menus) reads every stop on the shared scroll frame, returns which are on screen as state that changes only when a stop enters or leaves, and writes how far through each stop the reader is as `--nav-progress-<index>` on the header. Large screens show the stops across the header; smaller ones get `MobileMenu`, a real button that opens a full screen `<dialog>` with each stop in its zone's colour (`ZONE_ACCENTS`). A stop can list `parts`, sections inside its run that a reader looks for by name, or places inside one (Payments' five drawings, each linked by its `anchor`; the game world's Skills, Case studies, Projects, Recommendations and Arena): a list that opens under the stop on hover or keyboard focus on large screens, chips under it in the phone menu, their names in `menu.parts`, and a test keeps each inside its stop. The first link on the page is Skip to content (`menu.skip`), which lands on the `<main id="main-content">` that `Layout` wraps round the content, and the header's Email me sits beside the view switch on large screens.

Skill forge station ids are derived from the station title by `skillStationId()` in `src/config/skills.ts`, which strips every non-alphanumeric character (`"AI Tools & Enablement"` → `section-skills-AIToolsEnablement`). Renaming a station title changes its id, so grep for the old id when you do. Stations come from `portfolioData.skills` groups in the order of `FORGE_STATIONS` (languages, frontend, backend, mobile, blockchain, cloud, CMS, tools, testing, integrations, observability, AI, design); each needs a `sections` intro under the same key, and a skill's years come only from roles and projects that list or mention it, so a new skill needs that evidence (or a `SKILL_ALIASES` entry) or it shows as untracked. A long role lists everything it used over its life, so each skill also has a floor (`skillFloors()`): the later of its public release (`SKILL_RELEASES`) and when Red first used it where that is later (`SKILL_FIRST_USED`), and nothing counts before it. A new tool needs its release month there, and a test refuses a floor that names no listed skill. `SKILL_MENTION_EXCLUDE` keeps names out of the prose scan where the prose names them without using them. Skills by Area must not repeat a skill that has a forge bar; a test checks it.

### Tabs

Every row of tabs uses `useTabs` (`src/hooks/useTabs.ts`: roving focus, arrows, Home and End via the tested `rovingTarget` in `packages/accessibility/roving`) and the shared look in `src/components/Tabs`; a row whose open tab its owner keeps (the hangar's two rows) passes `active` and changes it in `onSelect`. Content tabs (Skills by Area, the skill forge's stations, the services' groups, the expertise tiles) render every panel and hide the closed ones with `hidden`, so all of it stays in the server HTML. A horizontally scrolling row carries `data-scroll-x`, which tells the project dialog not to treat its arrow keys as travel between regions.

### Styling: twin.macro + styled-components + Tailwind

Tailwind classes are compiled at build time through `twin.macro` (a babel macro; see `.babelrc.js` and `babel-plugin-macros.config.js`) into styled-components. Two idioms are used throughout:

```tsx
const Section = tw.div`relative px-[30px] py-[50px]`;              // static

const List = styled.ul(({ isCircle }: ListProps) => [               // prop-driven variants
  tw`list-none text-sm p-0`,
  isCircle && tw`flex flex-row flex-wrap justify-evenly`,
]);
```

Keyframes used from Tailwind classes (`wave`, `loading`, `border-transition`, `scroll-cue`, …) are plain CSS in `src/styles/globals.css` and referenced from arbitrary values, e.g. ``tw`animate-[wave 1s linear infinite]` ``; keyframes shared between styled components (`caretBlink`, `fadeIn`) are in `src/styles/keyframes.ts`. `tailwind.config.js` also registers custom `child`/`child-hover` variants and a `bg-wave` gradient.

Repeated style fragments live once in `src/styles/mixins.ts`: `media` (the breakpoints, and `media.reducedMotion`, which is not a media query but the root's `data-motion="reduced"`, written the same way, `${media.reducedMotion} { ... }`), `noAnimationWhenReduced`, `noTransitionWhenReduced`, `hiddenWhenReduced`, `honourHidden`, `focusRing`, `squareBullet`, `svgFill`, `progressText`, `accentFillOnHover`, `brightenOnHover` and the voyage HUD's `voyagePanel`; use them rather than writing the block again.

Shared pieces live in components rather than being restyled per section: `Section` and `Anchor` (`src/components/Section`), and the action buttons, filter chip and tag pill (`src/components/Controls`; an action takes its colour from `--action` where a parent sets one). A component whose styles outgrow it keeps them in a sibling `<Component>.styles.ts` (the mobile menu, the architecture drawing, the region dialog, the glance views), leaving the component its markup and behaviour. Animate `transform` and `opacity`, never layout properties such as `bottom` or paint heavy ones such as `box-shadow`, and avoid `backdrop-filter` on anything that sits over scrolling content.

### State: React Context, one folder per feature

There is no state library. `src/pages/_app.tsx` wraps the page in `AppLoaderProvider`, `PreferencesProvider`, `LensProvider` then `GameProvider`, and each feature colocates its state:

```
src/components/Game/context/GameContext.tsx    # createContext + Provider holding useState, value memoized
src/components/Game/hooks/useGameStateHook.ts  # useContext, throws if used outside the provider
```

Components call the `use*StateHook`, never `useContext` directly. `AppLoader` holds `isLoading` and `isReady`. `Game` holds the visitor's run: the chosen character and Bug Raid best (kept in `localStorage` under `redgame.game`, read after mount so hydration matches), plus this visit's bosses defeated, zones crossed and duels won, which the HUD and the finale read. Every `localStorage` read and write goes through `readStored(key, guard)` and `writeStored` from `packages/browser/storage`, which survive blocked storage and validate what they read. State that belongs in the URL hash (the industry filter, the case study audience, the map's games link) uses `useHashState` or the read only `useHashValue`, which keep every reader of the hash in step.

### Audience views (lenses)

The page has three views: `recruiter`, `product` and `engineer` (`src/config/lenses.ts`). `LENS_SETTINGS` sets what still differs between views: how much text decodes (headings only or all), the game layer (HUD, boss health, the fight, character select, the live table) and the depth of the wording. Every view, on every screen, gets the animated world, the zone crossings, the switch effects and the game layer; phones get the same features as desktop, with the HUD as a bar along the bottom. The backdrop starts at full quality everywhere and steps its sharpness down only if `watchFrameBudget` sees a device's frames run slow. Components read `useLensStateHook()` for `lens` and `settings`; `data-lens` is also set on the root.

Status runs `pending` (storage not read yet), `choosing`, `entering`, `chosen`. A `?view=` link wins, then the choice remembered in `localStorage` (`redgame.lens`); otherwise `LensGate` (`src/components/Lens`) shows a character select after the loader and plays that view's entrance. The server and first client render are always `engineer`, the full page, so hydration matches whatever was chosen. `LensSwitch` in the header changes view by going back to the top and playing that view's entrance, so the reader sees the immersion they picked.

Every section renders for every view; only depth and wording change. A section intro can carry `lenses: { recruiter, product }` descriptions, rendered by `SectionText`; titles never change, since the menu and the trail use them. History entries carry a `productOutcome`, boss fights read as problem, decisions and takeaway outside the full view, and `Glance` adds a fact sheet (recruiter) or product playbook (product) after the cover (its `GlanceSheet` is a dynamic import, so the default engineer view never downloads it, and the lens entrance is fetched the same way when a choice is near), pulling skill years from the forge and levels from the roster rather than typing numbers twice. The recruiter's glance has a Hiring for row (`hires` in `src/data/lens.ts`): each role leads with a fit line drawn from what the page already says and swaps the role years and skills, and the pick lives in the hash (`#hiring-<id>`, `hiringAnchor` in `config/sections.ts`) so a shortlist can be shared. Proof figures carry an `id`, and anything that shows one (the product playbook, the terminal) picks it by id, never by its value. The recruiter's entrance shortlists a candidate card whose ticks are the page's own facts (`LENS_CANDIDATE` in `Layout`).

### Blueprints

`src/components/Blueprint` draws kinds of architecture from `src/data/blueprints/`, one file per section (`ai`, `chain`, `delivery`, `platform`, `payments`, `casino`, `mmo`, each a default export; `delivery` is the integrations, delivery and observability of the commerce platform Red works on now, under More Skills by Area), plus `ventures.ts` for Red's own ventures and projects (the Freight Delay workflows among them), whose project map dialog names its drawing by `deepDive.blueprintId`. Only `labels.ts` is part of `portfolioData`. **Neither the drawings nor the code that draws them are in the page bundle**: a section renders `<BlueprintSection section="chain" />`, which fetches that section's file and `BlueprintList` together once it is within a screen of view (`loadSectionBlueprints` in `src/data/blueprints/index.ts`), and a dialog renders `<VentureBlueprint id />` on open. `src/components/Blueprint/index.tsx` exports only those two loaders, so never import `Blueprint`, `BlueprintList` or `BlueprintTabs` from page code, or the whole family lands back in the main chunk. Blueprints are therefore not in the server HTML. Tests read every drawing through the static `src/data/blueprints/all.ts`, which the page must never import. A new section of drawings needs its file, a case in the loader's switch and an entry in `all.ts`. Blueprints never name an employer, only the shape of the system, and a test enforces it. Each has three tabs: Overview (role, scale, stack), Architecture and Product flow (wireframes and user journeys). An architecture is groups placed on a grid (`place: { col, row, colSpan, rowSpan }` on wide screens; narrow screens stack in array order) with nodes inside, and edges between node or group ids. Wires are routed from the measured boxes (`utils/route.ts`, tested), measured from layout offsets rather than bounding rects so a tab switch that scales or flips the drawing does not skew them. A drawing is always a diagram: where it has less room than `minWideWidth()` (`utils/layout.ts`, which grows with the densest frame) it is laid out at that width and either scaled down to fit (the default, the whole system at a glance) or zoomed in to pan sideways. The wires are also listed as text for screen readers. A test keeps every drawing within 800px, the room a dialog has. In sections a blueprint bleeds up to 1200px wide on large screens, leaving 80px each side for the fixed rails; in a dialog it passes `isBleed={false}`. Overviews never identify a company: they say what was proposed and built, with a scale that names no one. A section with several blueprints shows them as tabs (`BlueprintTabs`, short names in `tab`) with an animated switch that belongs to its universe (`ZONE_EFFECTS`): a neural beam for AI, blocks confirming in a wave for Web3, a card dealt and flipped for the casino, a pixel dissolve for the game world, a terminal scan for engineering, a drop out of warp beyond; a plain fade in the quick view, nothing with reduced motion. Each zone gives the boxes its own look. Engineers open on the architecture, product readers on the product flow, recruiters on the overview. Every architecture carries a note that it is a glance, not the full design. The data test checks every edge joins ids that exist.

### Switches, carousels and games

Anything that switches in place uses `SwitchStage` with `useSwitch` (`src/components/SwitchStage`): call `play(direction)` on every switch and it plays the effect of the section theme the stage sits in where it has one (`THEME_EFFECTS`: What I Have Built is drafted tile by tile like a plan, a pen tracing each tile's frame over a drafting grid; each of More Skills by Area's areas opens in the way of the universe it belongs to on the journey (its `universe` in the content, `AREA_EFFECTS`: mined as blocks into a chain for Web3, dealt face down from the tab and flipped for iGaming, popped in as 8-bit pixels for game development, lit by the neural beam as it crosses for the AI areas, printed out of a till's slot for payments, typed out behind a block cursor for the engineering areas, dropped out of warp for DevOps and release), and its drawings boot like a live system, each box flickering on in turn and the wires after (`aimBurst` measures each skill once per switch: its way back to the tab as `--from-x` and `--from-y`, how far across the panel it stands as `--x`); both animate the content's own items, marked `data-switch-item` with their place as `--i`: tiles, skills, and a drawing's boxes, overview rows and tags, wireframe steps and journeys, so a themed section's drawings switch the same way, worked examples drafted box by box; `themeOf`; Code Review has nothing that switches, so it takes only its colour, and its activity draws a monthly line chart, lights its grids week by week behind a column of dots and pours its pull request squares in corner to corner), else of the zone it sits in, read from document order by `zoneOf()` (scan for the matrix, beam for AI, blocks for Web3, a dealt card for the casino, pixels for the game world, warp beyond; a test keeps every zone's effect different), or a fade in the quick view; a blueprint passes its own zone. Its direct children animate, and a child that comes back from `hidden` replays, so panels kept in the page need no remount. Under reduced motion nothing animates and the layers a switch lays over an item (a block, a card's back, pixels, a cursor) are never drawn. Skills by Area, the expertise tabs, the blueprint showcases, each blueprint's Overview / Architecture / Product flow switch and every `Carousel` use it. `Carousel` (`src/components/Carousel`) shows a page of cards at a time, keeps every card in the page, and drives Characters I Play and the boss fights.

The payments section (`src/components/Payments`, a stop of its own after Web3 and before Engineering, in its own teal theme) is a shop counter the reader pays at (`PayTerminal`, loaded once the section is near) above the payments blueprints, drawn on canvas by the rig engine (`packages/graphics/checkout`, hosted by `Payments/scene/CheckoutScene`): a smart terminal on a stand, the cashier's hand keying the amount on its screen and opening the app that fits the way to pay (`payAppOf`: card, QR pay or crypto), then the customer's hand bringing the card or phone, a chip card's PIN keyed on the screen, the receipt printed; the reader plays the customer. Each payment rings up a new total in the visitor's own currency (`tillService` in `src/services/payments/till.ts`, on `packages/finance/money`: the region from where their clock is set, then from their languages, its currency, a total priced as that currency's tills price, written in their language; `TILL` in `src/config/payments.ts` the fallback), handed down to the counter as a `CheckoutAmount` (the text, the sign before and after the figure, and the characters keyed, so a grouped or suffixed amount keys right and the keypad's decimal key shows the local mark) and told to it in place (`CheckoutActor.rebill`, which keeps the frames already cached), never rebuilding it; a counter retired as it is rebuilt for another way to pay is never driven again (`isGone`), so no frame loop is left behind and the page counts the approval from the new one's start. It runs at a real counter's pace (the story is timed in milliseconds, `storyMs`) under a camera that pushes in on the screen, follows the fingertip, moves to where the card meets the terminal and pulls back on approval. The hands and what they hold are 3D (see 3D stage): real hands on the WebXR joints, the card a 3D card in its issuer's finish (`PAYMENT_LOOKS`' `card`: the holder's own red card with his portrait as a halftone, from `payments.terminal.cardholder` and `portrait`; brushed space grey and midnight blue metal; velvet matte; frosted clear; laminated gloss; no other issuer's name or logo), drawn between the 2D terminal and the lens's vignette (`packages/graphics/checkout-stage`, loaded with the stage). No hand ever passes into the terminal or into what it holds: each is held by a grip the hand's flesh never enters (see 3D stage), a card or phone as far off the glass as the hand holding it reaches behind it, a pointing hand leans until its fingertip is what touches, and a card in a reader is cut where the terminal's body takes it (`hiddenInside`). ### The voyage

Saying yes in orbit opens the voyage (`games/voyage`, hosted by `Finale/Voyage/`), a full screen `<dialog>` whose code loads on first open. It is built like a small game engine, in layers that each know only the ones below:

- `packages/physics/newtonian`: the physics as pure functions. `GravityField` sums Newton's pull from every source, with each distance floored at the body's surface so a close pass is never flung to infinity, and a source with a `horizon` (a black hole) pulls by the Paczynski-Wiita law, mu / (r - rs)^2, which puts general relativity's innermost stable orbit at three Schwarzschild radii (`innermostStableOrbit`); symplectic Euler integration, exact exponential damping, circular and escape speed, tidal acceleration and Schwarzschild time dilation; an exponential atmosphere, drag in proportion to density times speed squared and entry heating to density times speed cubed.
- `packages/games/engine`: the engine, with no game in it. Entities are numbers, components live in sparse set `ComponentStore`s (dense arrays, so a system walks values without lookups), `World` despawns at the end of a step, a typed `EventBus` carries what happened, `SystemPipeline` runs the systems at a fixed 120 Hz with an `alpha` for drawing between steps, `Camera` is a critically damped spring with look ahead, zoom and trauma shake, `SpatialHash` keeps contact checks to what is near, `Pool` reuses objects and `RenderPipeline` draws layers in order.
- `packages/graphics/webgl`: `LensingPresenter`, one fragment shader that bends the canvas behind it round each black hole (the point lens deflection, the shadow, the photon ring, edge samples mirrored so nothing goes black). It hides itself while no hole is on screen; where WebGL is missing the 2D lens is drawn instead.
- `packages/physics/kepler`: where things are in the real sky. `heliocentricPosition` solves Kepler's equation on JPL's approximate elements (good from 1800 to 2050), `poleVector` and `subsolarLatitude` read a body's season from its IAU pole, and `earthSubsolarPoint` puts the Sun over the right longitude from sidereal time, so day and night on Earth fall where they really are.
- `packages/graphics/globe`: planets and stars on the GPU. `WebGLGlobeRenderer` draws each globe fresh every frame with one fragment shader, only the part on screen at the target's resolution, into its own canvas that is then copied into the 2D one: a real map (or a noise recipe per `SurfaceKind` where there is none, so a generated world needs no texture), day and night from the light, city lights on the night side, drifting clouds, the Sun's glint on water, air at the limb and a sunset band along the terminator, aurora, crater scars, rings with shadows both ways; a second shader draws stars (granulation, sunspots, limb darkening, corona, flares). `globeFrame` poses a globe from its light (north stays up, `northUp`, unless the light passes overhead; a body that keeps one face to another turns by `facing`). `CanvasGlobeRenderer` is the fallback without WebGL. `pow` is undefined for a negative base in GLSL, so shaders square with `sq`.
- `packages/games/voyage`: the game. The solar system is content with real values (`SolarSystemSource`: JPL's elements for every planet and Pluto, the major moons on circles, radii, surface gravity, air pressure and temperature, ground temperatures by day and night, the length of each day, IAU poles, rings) that runs through a guard, a validator and `SystemMapper` (`SystemService`) into a `StarSystem`: the Sun at the centre, distance from it in world units the square root of the AU from Mercury out and a log curve down to the Sun's surface inside (`utils/scale.ts`, which also maps back for telemetry), radii compressed by a power, moons out from their planets by the square root of their distance in its radii, each pull from the body's real surface gravity times one scale (the Sun's capped so a sound ship can climb out), and air with a density from pressure over temperature. `VoyageSimulation` runs one system per file under `systems/`, in order: orbits, navigation, phase, boosts, control, gravity, atmosphere, thermal, malfunction, aliens, weapons, motion, surface, descent, gates, stranded, collision, salvage, stations, projectiles, impacts, capture, phenomena, health, weather, traffic, wrecks, distress, spawn. `OrbitSystem` (`placeBodies`) moves every body on the mission clock, which starts at the visitor's real now and runs `hoursPerSecond` hours a second, or as fast as the pilot's `voyage-clock` setting picks (`clock.speeds`: real, half an hour a second, or six hours, when the Moon goes round Earth in under two minutes; `setClockSpeed` rebases the clock with `rebaseClock` so a change mid run jumps nothing, and the daily voyage keeps the usual rate so everyone meets the same sky). `VoyageGame` hosts it on the frame loop, flies the camera, turns the pointer or keys into intent, takes the real maps as they arrive (`setTexture`), zooms and opens the map; `TelemetryMapper` and `SnapshotMapper` turn the world into what the UI shows.

Landing is the real way down, not a cut. Touching a rocky world gently enough (`SurfaceSystem`) pins the ship to it and starts a descent (`DescentSystem`, `state.descent`): `planLanding` in `games/voyage/landing` picks the world's real method from its own air (density, scale height and speed of sound from the source's pressure, temperature and the gas's molar mass, `airFromSurface`) and gravity, so ours get theirs and every made world the one its air calls for: parachutes then landing rockets or a splash for a crew capsule home (Soyuz and Dragon), a supersonic parachute then the engine on Mars, parachutes all the way on Titan (Huygens), a parachute then a drag plate on Venus (Venera), the heat shield then the engine where no parachute could open in time (`retroBurn`, as a reusable booster comes home), and a powered descent from orbit where there is no air worth having (Apollo), from above the air where it is too thin and shallow to slow the craft. Each way is taken only once the guidance has flown it ahead (`flyAhead`) and it lands in one piece, so the autopilot never crashes on a made world; the flight is remembered by plan, so `rehearse` does not fly it again. `stepDescent` steps it through the physics (gravity falling off with height and eased by speed across, exponential air, drag, a capsule's lift held up while it falls and banked away as it levels, which keeps the load near 4 g without skipping out, reefed parachutes, entry heating told against a capsule's peak, guidance that keeps a powered fall stoppable and lines it up with the braking so it passes the low gate slow and upright, landing rockets throttled to the steady braking that reaches the touchdown speed just at the ground). It plays `config.descent.speedUp` (40) times faster than life, never longer than `longest` (15 s), timed by `rehearse` once per world and run; the reader's `landing-time` preference can make it real time, and `landing-control` can hand the burn to the pilot at the 150 m low gate, flown at life's pace with a held press or the burn key (`VoyageGame.press`) and a reserve of burn. The landing counts, scores and pays only at touchdown; down harder than the craft takes (`safeSpeedOf`), the legs give way and the hull pays. No take off until it is down and settled (`settleSeconds`), except under fire, when a burn aborts the landing up to the low gate (below it, the pilot's burn is the landing engine). Coming down, a burn is the burn key or a held press, never where a mouse happens to rest. Home, nobody flies the capsule again (`state.homecoming`): the recovery ship comes alongside at sea or the recovery helicopter sets down on land for `config.descent.recoverySeconds`, then the mission clock moves on `recoveryDays` (three) with every world placed where the days took it, the ship is renewed (`recovered`), and the view goes to the home pad (`HomePad`, the finale's launch site handed to `VoyageGame` as `home`) with the Sun where it really stands over it and the new rocket beside its tower; only then can it launch. While a craft comes down, the air it feels is the real air at its height (`AtmosphereSystem`), so Venus crushes a weak hull only in its last kilometres. `VoyageGame` reads whether the spot is open water from the surface view and tells the simulation (`setGround`), so a capsule at sea splashes down. The surface view draws the craft at its real altitude (the air thinning to black with an edge on band of air at the horizon, the land flattening far below through the painter's `nearness`), an aeroshell in its plasma through entry, the canopies of each phase (`canopiesFor`), the drag plate, the flame as long as the throttle, dust and the splash; the card reads the phase, altitude, speeds, load and pace (`descentRows`).

The reader's settings (how much the page moves, the terminal's single key shortcuts, which a reader can turn off for WCAG 2.1.4, how landings are timed and flown, how much space slows the ship, steering by tilting, how much of the voyage's HUD shows) live in `src/config/preferences.ts` (`SITE_PREFERENCES`, a schema for `settings/preferences`), their words in `src/data/portfolio/preferences.ts`, one `PreferenceStore` for the site in `src/services/preferences/store.ts` (kept in `localStorage` under `redgame.preferences`, read after mount), read in components through `PreferencesProvider` and `usePreferencesStateHook`, and changed from the hangar's Settings tab (`SettingsPanel`; the motion and shortcut settings on the accessibility page instead) or the terminal (`settings`, `set <setting> <value>`, `reset [setting]`, in `services/terminal/commands/settings.ts`). The flight is open space, point to fly: the ship turns towards the pointer and burns harder the further away it is (no press with a mouse, a finger held on phones), or arrows and WASD (`heldSteer` in `Finale/Voyage/controls.ts`: by the `voyage-keys` setting, flying the way they point on the screen as a thumb stick leans, Space braking, or turning and burning), held keys winning over the pointer, which steers again only once it moves after they are let go, or with the `tilt-steering` preference on a phone or tablet the way the device leans (`useTiltSteering`, the pure `screenLean` and `tiltSteer` in `Finale/Voyage/tilt.ts`, level being however it was held when the flight began, `askToTilt` asking iPhones first); each kind of space sets how fast the ship can go (`mediumAt` in `systems/medium.ts`: a void fastest, then open space, a nebula universe's haze, belts, nebulae and rings, `config.medium`), the limit easing between them (`state.speedLimit`), or with the `space-drag` preference set to real, only the engines; the wheel, a trackpad's pinch (a wheel with the control key held, or Safari's gestures, through a listener that keeps the page's own zoom out of it), a pinch or + and - zoom, M or a press on the radar (`MapLayer.radarAt`, `VoyageGame.isOnRadar`) opens the map, a view of its own: the HUD and its cards step aside for a bar with the way back, Escape closes it, and its station and mission marks carry no words (the key explains them, so nothing piles on a world's name). Every planet, moon and the Sun pull, so slingshots work and a ship left alone drifts sunward. Air is read at the ship's underside. Heat is one temperature the hull drifts towards (`environmentAt`): sunlight's equilibrium at the real distance, the cold of space in a planet's shadow, the air's own temperature, the ground's by day or night when landed. Each of the ship's systems (`Modules`: hull plating, engines, shield generator, sensors, fuel tank, radiators) has a rating in `ThermalConfig.ratings` and wears past it, so near the Sun they fail in order, sensors first, and fuel boils off past `boilOffC`; heating in a star's light, the pilot is warned once the hull is within `warnMarginC` of the first harm (a ship left alone falls sunward, so the warning comes early enough to burn clear), and again only after it has cooled as far below. A failing system shows: engines push less, shields hold no more than their generator allows, telemetry goes dark without sensors, a holed tank leaks, failing radiators slow the cooling. The solar system is the warm up (`isSolarSafe`): the hull keeps a floor against rocks, crashes, entry and crushing, and an emergency burn throws the ship out of a giant's depths, but not against melting in the Sun. Past the Kuiper belt (`edgeAu`) the singularity wakes ahead of the ship and takes it whatever it does; it is lost, then wakes in a universe per zone crossed (`VOYAGE_THEME` in `config/theme.ts`), where nothing is safe and black holes throw it to one it has not seen. Those holes are real stellar black holes: 5 to 30 Suns, lighter ones commoner, each pulling as a star of its mass (`pullOfMass`, shared with the stars, so dead stars pull by their mass too) and with a horizon in proportion, so a heavy one outpulls the engines from several units off and nothing circles inside three horizons; tides tear at a ship close in (`tear` in `systems/damage.ts`, one limit for dead stars and holes), further out by a light hole than a heavy one, capped so a plunge goes through to the next universe while lingering close is fatal. Past the singularity every universe is made from the run's seed (`UniverseGenerator`, the seed's first draws thrown away because a Park-Miller generator follows its seed at first): the first five take the site's zones for their look and names, the rest pick a deep style (nebula, void, crystal, ember, abyss) and are named from syllables in the content (`universeNames`). Each sits in a galaxy of a real kind (`config/galaxies.ts`: spiral, barred, elliptical, irregular, dwarf, ring), which sets which stars are found (`STAR_WEIGHTS`: young blue stars and supergiants in spiral arms and starbursts, old red stars in ellipticals), how rich in metals its worlds are, and its sky (`paintGalaxySky`: a band with a dust lane from inside a disc, a gold glow inside an elliptical, a dwarf's great neighbour overhead). Each is a `StarSystem` like ours, so orbits, gravity, air, landing, heat and the globes all work there. Its star is a real class (a void has none, its worlds rogues lit only by starlight; `config/stars.ts`, each from a star we know: a brown dwarf, red, orange, yellow, white and blue dwarfs, a red giant, blue and red supergiants, a hypergiant, a Wolf-Rayet star, a white dwarf, a neutron star), sized by the same rule as the worlds and laid out so its warm zone falls where it really does (`scaleFor`: the square root region begins at ten of its radii or 0.3 of the square root of its luminosity in AU, so a red dwarf's worlds crowd close and a supergiant's lie hundreds of AU out, within `FURTHEST`). Many share their system (`MULTIPLES`, as surveys find, massive stars most): a close pair circling the centre in days with circumbinary worlds well clear of it, a wide pair whose partner keeps three and a half times beyond the brighter star's worlds (`S_TYPE_LIMIT`), or a close pair with a third far out (red supergiants and hypergiants are drawn alone, since a partner far enough out to leave their worlds room could not be reached); every star pulls, lights, heats (`lightAt` sums their light, the heat comes from the brightest), glows from off screen by its apparent brightness, and stands in the sky from the ground. From the fifth universe on some are mazes (`network`): three to eight systems joined by gates in a web with dead ends and loops (`GateSystem`, `systems/gates.ts`), each system made from its own seed with worlds of its own and kept as it was left, the way on (its black holes) only in the system furthest from the way in, the compass leading through what is known of the web to somewhere new (`nextHop`), and the map showing the web as far as it is known. Its worlds are the classes found round other stars (`config/worlds.ts`: iron, lava and carbon worlds, Earth-like, super-Earths, ocean worlds, eyeballs locked to red dwarfs, Venus and Titan likes, mini-Neptunes, ice and gas giants, hot Jupiters, super-puffs, chthonian cores), spread evenly in the logarithm of distance from inside Mercury's orbit outward, each at least 1.4 times further out than the last within the room the star and any partner leave (`spreadOrbits`, fewer worlds where there is less), each kind chosen by its equilibrium temperature and the galaxy's metals, its size, pull and air from its class, its look true to it (`generators/looks.ts`: Sudarsky's colours for giants, plants coloured by their star, the GPU's eyeball and hot Jupiter recipes), its moons spread as real moons are on Kepler periods for its mass, and its name lettered as astronomers letter them ("Veldara b", a pair's "Veldara AB c", a moon "Veldara c II"); a belt of rocks has an id of its own and is named for its star from the content (`universeNames.belt`). About half the worlds life could arise on belong to one of the universe's factions (`inhabitants`, never a world of our own system): their cities light the night side (`cities`, the globe shader's `u_cities`) and stand on the horizon from the ground (`paint/settlements.ts`); a peaceful or neutral people welcome a ship that lands among them (mended, refuelled and given a gift, paid as `income:hosts`), and a hostile or territorial one fires from the ground below `descent.fireAltitude` for as long as it stays (`groundFire`, enough that staying is fatal but a pilot who takes the last 150 m by hand can still land a sound ship). Every system that reads `isInSystem` now runs in universes too; `isSolar` keeps what only belongs at home (the edge, the singularity, Earth's aurora, telemetry in AU). Who lives there are its factions (hostile, territorial, neutral or peaceful, each with a hull shape, colours, a gun, a level, pack size, speed, aggro and leash radii) and `AlienSystem` runs them as an MMO's mobs: packs round the ship's path, threat from being seen and from damage, the whole pack roused together (`damageAlien`), leashing home to heal when chased too far, the badly hurt fleeing, fights kept within sight (the camera pulls back to frame attackers and red chevrons point to those off screen), and a boss after `bossAfter` seconds that calls adds and fires faster as it weakens. Peaceful traders and void whales never fight. The ship's gun aims itself (`WeaponSystem`, leading its target with `leadDirection`): what the player clicked to lock first, then anyone coming for the ship, then rocks headed for worlds, then a rock about to hit; never the peaceful unless locked; F holds fire; every shot warms the hull and makes noise. `ProjectileSystem` lands shots through the spatial hash. In our solar system rockets and starships pass by (`TrafficSystem`). Rocks set out for worlds (`ImpactSystem`) with a warning, aimed by following their path through the same gravity field (`predictApproach`) until it hits; a hit weighs kinetic energy (arrival speed including the world's escape speed) against gravitational binding energy (`impactEnergy`, `bindingEnergy`): a crater sized by the Collins scaling law (`craterKm`, drawn on the globe and cooling), a burst in thick air, a melted hemisphere, or the world shattered into rubble; shots chip a rock's strength and push it by their momentum, so a small one can be deflected and a planetoid only broken into pieces that may still hit. `PhenomenaSystem` runs a universe's strange things: nebulae, pulsar beams, magnetars, a supernova that warns then sends a shock front a world's shadow spares, gamma ray bursts that line up then fire, the dark forest that hears engines and guns and strikes from far off, wormholes, quasar jets, and the tides of dead stars. Each universe starts empty of the last one's ships (`clearSpace`).

Progress is kept between runs, and only in this browser: no account, and nothing is sent anywhere, except a daily voyage's run the pilot chooses to put on the day's board (only the initials they type and the score). `src/services/voyage/pilot.ts` opens a `PilotRepository` on `browser/store` (`createStore("redgame.voyage", { size: "large", isDurable: true })`: IndexedDB, else localStorage, else memory) and reads back a `PilotProfile` checked by `isPilotProfile`; `usePilotSync` saves shortly after each change, at once when the page is hidden or left and when the dialog closes, and keeps tabs in step (a tab that saved says so on a `BroadcastChannel`, and another with nothing of its own waiting takes that save on); the hangar's reset wipes it. A pilot moves to another device with no server: the hangar's Settings (`Hangar/PilotTransfer`) shows a link carrying the pilot in its fragment (`#pilot=`, packed by `encoding/compact`; a browser never sends the fragment), drawn as a QR code by `uqr` (loaded on use) when it is short enough to scan, and the same pilot as a file (`browser/files`' `saveBlob`); a file opened there is read like the device's own (`readPilot`, the store's `readVersioned`: migrated, repaired, checked) and, once the pilot agrees, taken on in place (`usePilotSync`'s `adopt`). A page opened with a pilot link shows `PilotArrival` once a view is chosen, which writes it as this device's pilot (`landPilot`) and tells open tabs on `PILOT_CHANNEL`. Opening IndexedDB gives up after 1.5 seconds and falls back, a write counts only once its transaction completes, and the connection closes with the dialog. A ledger entry that no longer checks out is left out on its own (`Ledger.recover`), never the whole wallet, and a career, armoury or progress that no longer checks out starts again on its own (the repository's `repair`), never the whole pilot. A piece's experience is kept whole (fractions carried in memory, never saved). The economy lives in `games/voyage/economy/` and never touches a run itself. `Hangar` holds the ship's level, a `Backpack` limited by room rather than kinds, the plans found, and a `Wallet` that is a double entry ledger (`finance/ledger`) in Red Coin and Void Shards: every coin comes from an income account named for the deed and goes to an expense account named for what it bought, and old entries close into one opening balance. Deeds pay (`REWARDS`): a new place, a first landing, a hostile's bounty by level, a world saved, a boss, a universe reached, and the run's points at the end; gold Red Coins drift in space (and fall from rocks shot apart), are drawn in once the ship is within `pickups.magnet` and pay as they are picked up (`income:coins`). Every rise in Red Coin or Void Shards floats up off its count in the HUD (`useGains`), so where coin comes from is seen as it comes in. Things come from `CatalogLootTable`, which answers the simulation's `LootTable` port: derelicts drift by (`WreckSystem`), the fallen leave hulks, rocks and comets shot apart leave ore and ice, and salvaging means coming alongside a wreck slowly, where a tractor beam matches speeds, and holding still (`SalvageSystem`); what the hold has no room for stays on the wreck (`returnLoot`). A find may be empty, each of the site's universes has a material only it gives (the deep ones' turn up rarely elsewhere in the deep), and plans turn up in wrecks and on bosses. Ships break down (`MalfunctionSystem`: misfire, fuel leak, coolant leak, sensor glitch, shield emitter, hull breach), likelier as a system wears, runs hot or flies in the universes, and are fixed from the hold: the fault's own part, a field repair from salvage, or a repair kit (`FAULT_FIXES`), its part made first when a known plan and the hold allow (`repairPlan`); landed on any world, the crew patches the oldest fault up for nothing every few seconds, so a pilot is never stuck, and each fault says what fixes it. A new pilot starts with a starter kit (`STARTER_KIT`). There are 30 levels, six hulls of five marks (`config/tiers.ts`: Rocket, Shuttle, Corvette, Starship, Intergalactic starship, Titan), each hull's first mark better at everything than the last hull's fifth; a Shuttle is built for Venus and the Corvette on fires lasers. An upgrade needs Red Coin, the hull's materials, Void Shards from the Corvette on, and for a new hull its blueprint (`upgradeCost`). What the hangar does to the ship comes back as `ShipEffect`s for `VoyageSimulation.apply`, and an upgrade refits the ship in flight (`refit`, keeping every bar at its share), drawn as its own hull with a chevron per mark (`paint/ships.ts`). `VoyageGame` joins the two: deeds and finds go to the hangar, and `act` and `follow` carry out what the pilot asks or the one suggestion `Hangar.suggest` ranks (a fault fixable now, a part to make for it, a consumable the ship needs, the next upgrade). The dialog's `HangarPanel` shows the ship, hold, plans and ledger; H opens it and holds the run still, U does whatever is suggested.

It draws on three stacked canvases: a back 2D canvas (backdrop, a universe's phenomena, the Sun and every body as GPU globes, storm fronts, the far half of each black hole's disk), the WebGL lens over it, and a front 2D canvas the lens never touches (the near half of the disk, rocks and comets, the living with MMO nameplates, rocks headed for worlds with their paths and strength, shots, the ship, effects, the overlay, the radar and the map). The dialog shows a target frame, a boss frame and the incoming rock as plain text over the canvas. The globes have a canvas of their own off screen. The real maps (`VOYAGE_TEXTURES` in `config/theme.ts`, NASA and USGS imagery, public domain, about 800 KB of webp in `public/images/voyage/`) are fetched only once the voyage opens, Earth first; `TEXTURE_IDS` in the package lists the ids the looks (`config/looks.ts`) name and a test keeps the two in step with the files. Rocks, disks and the ship are painted once at zoom 1 into a `SurfaceCache` (capped in size) and only blitted after; backdrops are small tiles that wrap without seams; exhaust, smoke, shards and molten drops come from one pooled particle system with a hard limit, smoke drawn behind the ship; halos are added light, so they glow rather than darken. Close to the Sun the view washes out with glare; the hull glows red, orange, then white as it heats.

A pilot also has a career (`games/voyage/career/`), kept in the same profile (version 4; the repository's `migrate` brings a version 1 profile up with a fresh career, a version 2 one with no boosts and a new pilot's bar, and a version 3 one with a stock armoury and fresh progress). `Career` keeps three missions on the board (`MISSIONS`, offered in order as rank allows, then contracts read back from their ids), each counting `CareerEvent`s through `advance` until it pays experience and Red Coin; the story (`STORY` in `career/config/story.ts`, its pure steps in `core/StoryBoard.ts`) runs a chapter at a time, out of our solar system, then one chapter for each universe of the site's zones in order and the sixth past them, a universe's chapter opened by reaching it and its other steps counted in any order after that (the launch's in any order from the start), paying as missions do (through the ledger as `income:story`), kept as `story` in the career (a career kept before the story began has none and starts it), and told in the hangar's Quests tab (`Hangar/Story.tsx`: the chapter under way and its steps as the main quest; every chapter told, with the line it decoded to, under Completed) and in notices (`storyStep`, `storyChapter` with the line of mine the signal decodes to, `storyOpened` as each chapter opens, once while the voyage is open); its words, every chapter's title, opening and line, are `career.story` in the content, each line drawn only from what the site already says; ranks come from experience (`RANKS`); the codex (`CODEX`) holds every world of our own system with its real figures from `SolarSystemSource`, and the kinds of world, universe, star, phenomenon, life, wreck, thing and boost found; and the daily voyage keeps each day's best. `PilotLink` joins a run to the pilot: deeds pay the hangar and count for missions (a mission's coin goes through the ledger as `income:missions`), finds go in the hold and the codex, a danger counts as lived through once the ship is still flying after it, and a run that ends is settled once; `VoyageGame` only hosts it. The daily voyage (`play("daily")`) starts at noon UTC on the day with every random draw seeded from the date and started over at every step from the step's number (`dayKey`, `dailySeed`, `dailyEpoch`, `StepRandom`; systems forget their timers through `System.reset`), so everyone flying it meets the same universes and the same flares, comets, rocks and wrecks at the same moments, whatever else they did differently; the best run of the day is recorded a few times a second (`GhostRecorder`, kept apart from the profile under its own key) and flies beside the ship as a translucent ghost (`GhostLayer`) wherever it was at that moment of its run. Photo mode (C, or the camera button) holds the view still without the HUD, the radar, the compass or the arrows, lets a drag look round and a pinch or the wheel zoom, and saves every canvas composed into one PNG (`VoyageGame.photo`). The hangar (`Hangar/HangarPanel`, its tabs laid out in `Hangar/tabs.ts`) is a flight deck: rows on thin rules, one framed panel (`Frame`, corner brackets) for what matters most on a tab, gauges in segments (`Meter`), each tab in its own accent (`--tab-accent`). Six tabs with icons (its own icon row, and the site's tabs for each tab's sections, both on `useTabs`): Pilot (the pilot card with the rank and the level side by side, and the talents), Quests (the quest log, `Hangar/Quests.tsx`: Active holds the story as the main quest, the missions as side quests, what comes next (`CareerView.upcoming`, those waiting for a rank saying which) and today's daily voyage with the way to fly it; Completed holds every chapter told and mission done, newest first, with what each paid), Ship (the sheet, the loadout, the forge, the style), Cargo (the hold, the plans), Log (the codex and the badges as tile grids that open a tile's details underneath, and the ledger, which a pilot sees as Coins) and Settings (with what is kept of the pilot and the reset), each a row of sections. A dot marks a tab and a section with something to do now (`sectionDots`: a talent point, a quest done since the quests were last looked at (`questsDone`), the upgrade paid for, an empty slot with something for it, a weapon to forge, a plan to make, codex finds and badges newer than those seen), each currency in the purse says what it is when tapped, the hangar's one suggestion sits under the header, it opens where it was last left (`redgame.hangarPlace`, the finds seen under `redgame.hangarSeen`) unless the voyage sends it somewhere, and a sideways swipe moves between tabs. One quest is followed on the HUD (`Tracker` under the bars in the left column, `trackedQuest` in `Finale/Voyage/quests.ts`): the story's next open step, or a mission pinned with Track in the quest log (kept under `redgame.trackedQuest`; Track pressed again goes back to the story). Like the rest of the HUD it lets the steering pointer through: only its scroll button, and the small chip after a line about a quest done (`isQuestNotice`), open the quest log. What comes next is listed in the order the board takes it. The Loadout picks a slot, then puts things in it with one press; the Style tab tries a paint on the ship before it is worn (`drawShipPreview` takes a paint) and says what wins a locked one. Notices queue in the hook and the dialog says them one line at a time, since one moment can bring several (a run paid, a mission done, a promotion): each stays as long as its length needs (`messageMs`), at most four wait (`queueLine`), kept lines (the story's, and dangers) are never the ones dropped, a danger (`isUrgentNotice`: a rock on its way, a supernova or burst lining up, a boss's attack, a storm, fire from the ground, the hull melting, a system failing, stranded, captured, lost) is said at once, and the answer to a press (`replyLine`) never wipes a kept line. A quest done shows as a card in the line's place (`questCard`: its kind, its name, what it paid, and for a chapter the line it decoded to), kept like the story's lines and staying at least `CARD_MS`. Money is never written as an abbreviation: `Finale/Voyage/Money.tsx` draws a Red Coin as the gold coins flown through in space look and a Void Shard as a violet crystal (`CurrencyIcon`, named for screen readers and on hover), `Money` and `PurseAmounts` put the mark beside an amount, and `fillNodes` fills a template ("Sell a Void Shard for {price}") with one.

Boosts are found, not bought. Now and then a glowing core drifts in just inside the view (`BoostSystem`, on `config.boosts` timers, sooner in the universes), one of the place's own more often than not (`boostToFind`): four turn up anywhere (afterburner, overcharge, tractor beam, decoy flare), three belong to our solar system and lean on its real physics (a solar sail pushed by the sunlight where the ship is, a magnetic shield that turns a storm aside, an ion drive that trades thrust for fuel), and each of the site's universes and each deep style has one of its own (bullet time, a wingman, a block shield, a lucky roll, a pixel blink, a cloak, a warp jump, a prism, a heat sink, a gravity well with real gravity); `BOOSTS` in `config/boosts.ts` sets each one's origin, weight, duration, cooldown and strength per level, and `BOOST_COLOURS` the colour of where it is from, shared by the core, the bar and the Loadout. Flying through a core emits `boostFound`, and `PilotLink` puts it in the hangar (`findBoost`: a charge, up to `MAX_CHARGES`, and a find towards the next of five levels, `LEVEL_FINDS`) and the codex. Using one goes through `VoyageSimulation.boost` (`activateBoost` in `systems/boosts.ts`, which refuses while it cools down, lost, captured, coming down, or where it could do nothing (`canWorkHere`)) and only then spends a charge; each boost works through the real systems (control, motion, health, damage, weapons, aliens, gravity, thermal, weather, collision), and the snapshot carries what is on, each cooldown and the blocks standing. The ability bar is six slots kept in the profile (`bar`, a new pilot's holding the starter fuel cell and repair kit, `newBar`), each a thing from the hold, a boost or a weapon (`BarSlot`), filled from the Loadout tab (`Hangar.setSlot`, a slot already on the bar moving) or by a boost's first find; keys 1 to 6 or a tap use a slot (`VoyageAction` `slot`, `VoyageGame.useSlot`) only while the run moves (not paused, on the map or in the hangar, and a held key once), and a press for nothing comes back as a `slotRefused` notice saying why. The profile guard checks only the shape of the boosts and the bar (`KeptSlot`): a boost a later release no longer knows is dropped as the hangar reads it, never the whole profile. A block shield's block takes one hit whole, so fire from the ground, which comes as a stream (`groundFire` damage), passes it by; a gate or a black hole leaves a decoy and a well behind (`clearSpace`); a jump that would end inside a world is refused, and a lucky roll lands only on a boost that can work there. The HUD is one CSS grid over the view (`Hud` in `VoyageDialog.styles.ts`), every panel in an area of its own, so none can cover another whatever it says (the overlap check holds it, see Verifying changes), in three layouts: an upright phone or tablet (the buttons, the readout and the place each a row across the top, then the column of bars with the ability bar (`Finale/Voyage/AbilityBar`) down the right beside it, from the column's top on a short phone, `media.shortPortrait`, with smaller slots, folded into two columns of three on the shortest, `media.shortestPortrait`; the voyage's line, the alerts, and along the bottom the radar and the telemetry), a wider screen (`media.voyageWide`: the place and the column down the left, the readout and the buttons along the top, the line and the alerts between the column and the telemetry on the right, the radar and the bar along the bottom) and a phone on its side (`media.shortLandscape`: as wide, the readout under the buttons, the bar between the radar and the corner, and a world's card in the telemetry's corner while it steps aside). The radar is drawn on the canvas, so `RadarSpace` keeps its room in the grid at the size MapLayer draws it. The column takes the room it needs short of the alerts' least and cuts off what has none; where there is room the first column is exactly the radar's width (the HUD's `--radar`), so the ability bar spans from the radar to the telemetry, and the place and the column span it and a second column, together at most 260px wide (`fit-content`), so a long place or a world's card wraps rather than squeezing the middle. The alerts stack up from the bottom, nearest the ship, the most urgent lowest (the rock, the boss, the countdown, a call for help, a salvage, a port, the suggestion, the guide); what has no whole room folds away (`useFoldedAlerts`, read again as the list or an alert changes size, marking `data-folded`), the line's room at the top kept only once one is cut, under one line saying how many more (`AlertsMore`), which opens them all to scroll through in the same room, only the alerts themselves then taking a press. The line has its own place on a wider screen and is a strip laid over exactly the readout and the place on an upright phone, and over the readout's row on a phone on its side (the one overlap by design), a quest's card cut to the strip's height from its top. A long name in a frame is cut with an ellipsis, its level and standing always beside it. Where there is room a world's card takes the radar's corner and the column beside it, the bar keeping to the middle (the HUD's `data-card`). The hangar and a port's trade are a drawer that takes the whole screen until the HUD has its wide layout, then a 460px column on the right, beside which only the place and the column down the left stay (`data-drawer`), the ship's state while it is mended or refitted. Each slot of the bar shows its key, what is left, a boost's level, a glow while it is on and a sweep while it cools; an empty slot opens the Loadout. A screen too small for the whole HUD (`SMALL_HUD_SCREEN` in `Finale/Voyage/hud.ts`, upright and at most 520px tall, or any phone on its side), or the `voyage-hud` setting (auto, compact, full), makes it compact (`hudLayout`, the dialog's `data-hud`, read by the styles' `COMPACT` selector): the buttons, the readout, the place, the four bars as thin colour bars, the followed quest on one line, a slim telemetry (speed and the next stop, `isSlim`), the ability bar, the radar, the strip and the frames, with every other panel (the ship line, the systems, the faults, the full telemetry, a world's card's details, though coming down it keeps the altitude and the fall) behind an info button beside the bars that wears a red dot while a system is hurt or a fault waits in flight, and opens the HUD in full until pressed again; per element differences are data attributes (`data-slim`, the alerts' `data-folded` and `data-expanded`), since styled-components writes an `[ancestor] &` rule against the component's shared class. `BoostsLayer` draws what is on round the ship (the well, the decoy's flare, the blocks circling, the wingman's drone, field lines, the sail, the tractor's reach, bullet time's green cast), and the ship's layer draws the cloak, the afterburner and the ion drive on the ship itself. The dialog reads boost names from the content (`isBoostName`), so it needs none of the game's code.

Gear makes the ship's sheet (`games/voyage/gear/`, the hangar's Ship tab, `Hangar/ShipSheet.tsx`). Every part of the ship is a slot (`GEAR_SLOTS`: cockpit, plating, engines, wings, shields, sensors, tank, radiators and the main gun, then pods, a reactor, a warp drive and a halo ring that a ship grows only at a form and a pilot level, `SLOT_SPECS`), and the piece in it (`GearPiece`: a base of six grades, a rarity, its experience and its enhancement) adds stat shares (`GearStat`) that `configForShip` lays over the hull's config, with a little for every pilot level. `Armory` keeps the pieces, what is fitted and the ammunition aboard; pieces level with use (`GEAR_CURVE` on `progression/levels`), are enhanced up `ENHANCE_LADDER` (`progression/enhancement`: ten moons, ten stars, ten galaxies, each try costing Red Coin and moonstone, star shards or galaxy cores, a failure falling three steps among moons, four among stars and six among galaxies, across tiers, unless a stabiliser holds it; the sheet shows the ship's total at its top), break down for coin, and weapons are forged from their plans (`forgeCost`). Six hulls of five marks make thirty forms, each drawn with its own parts (`paint/ships.ts`), with the grown pieces drawn on the hull. The pilot's `Progress` (`games/voyage/progress/`) holds experience to level 300 (`PILOT_CURVE`), one to three stars per universe and per daily voyage, fifty achievements read from lifetime counters (`ACHIEVEMENTS`, `COUNTERS`), the paints and engine trails they unlock (`PAINTS`, `TRAILS`) and the guided first flight's step (`Guide.tsx`). `ProgressLink` joins a run to both: experience for deeds, gear experience for hits, kills and damage taken, ammunition spent and found, gear in loot, caches and boss chests opened, streaks, stars, achievements, and a `RunSummary` for the card at a run's end. The cards before a flight and at a run's end are framed like the hangar's panels, their corners in the moment's colour: the first shows where the pilot stands (rank and level, coin and shards, the quest followed) and folds the controls under How to fly (open the first time the voyage opens); the last shows the score large and the run's figures as tiles.

Weapons go on the bar beside boosts and things from the hold (`WEAPON_SPECS`: missiles that home, mines dropped behind, a railgun through everything in its line, an EMP that stuns, flak that fans out and downs missiles), fired through `fireWeapon` (`systems/arsenal.ts`), each taking its own ammunition (`AmmoType`), found in wrecks, on the fallen and in caches and bought at stations, in racks that grow with the hull (`rackFor`). The main gun spends rounds; out of them, on normal (`voyage-difficulty`) it keeps a weak backup shot and on hard it falls silent. With `voyage-aim` on auto the guns pick their targets and spend faster; by hand, keys, a thumb stick (`TouchStick`, the left of a phone) or a controller's left stick fly, while the pointer, the right of a phone or the right stick aims and a press or the trigger fires. Hits throw damage numbers (`NumbersLayer`), a kill holds the world still a moment (not with reduced motion), `VoyageFeedback` turns events into sound and a score (`audio/synth`, through the `SoundPort`, `voyage-sound`, `voyage-music`) and a buzz (`browser/haptics`, `voyage-haptics`), and `PadControl` reads a controller (`interaction/gamepad`): the face buttons and shoulders are the bar, Start pauses, Back opens the map, up the hangar, down docks.

On reaching each universe and after each boss the run offers three perks to take one of (`PERKS`, `drawPerks`, `PerkCard`): most add stats for the rest of the run through the same `configForShip`, and the scavenger, vampire and quartermaster change how salvage, kills and ammunition found work; the run is held still meanwhile (`VoyageSimulation.isHeld`, `offerPerks`, `choosePerk`, which `advance` and `step` both honour). Stations keep orbits round Earth, Mars, Jupiter and Saturn and one world of each universe's system (`StationSystem`, kept by the people there if they welcome strangers, else a free port), and peaceful traders are ports too: alongside one slowly enough, E, the Dock button or the d-pad docks (`dock`), holding the run still while `StationPanel` trades in the hangar's look, a row of the sections the port has (Crew, Ammo with how full each rack is, Market, Sell; the crew marked when the ship needs one it can pay for). Calls for help come now and then from ahead (`DistressSystem`, an amber arrow and frame): survivors taken aboard by holding still beside the beacon (paid as `income:distress`), a spilled cargo of caches, or where hostiles live, an ambush. A boss shows each great attack before it lands (`systems/bossMoves.ts`: a nova's red ring, a charge's red lane, a volley's lock-on, more of them as it weakens). The universes have more wrecks (`salvage.away`), among them the hulks of those the ship brought down in earlier universes of the run (`state.hulks`), which say where they came from when salvaged. Stations and calls for help show on the map and the radar.

It keeps itself smooth on older phones. ### Ask Red

`ask <question>` in the terminal streams an answer read only from the site's content; `deeper` (or the Go deeper button) asks the same question at the deeper tier. Each answer ends with the model that wrote it. `src/pages/api/ask.ts` is the API route and only speaks HTTP: same origin only, 503 (the agent is resting) when no provider has a key or with `ASK_ENABLED=false`, and every decision is the domain service's. Keys live in Vercel's env and nowhere in the repo.

It is built in layers, each a package with the usual folders, so nothing is written twice:

- `packages/http/api-client`: `ApiClient` on fetchff, for JSON and streamed bodies, returning typed results instead of throwing. `ApiClient.global()` is the one shared client (`configureGlobal` sets it once); `withConfig` makes an instance that inherits from it and adds a base URL, headers or retry rules. The browser's Ask client uses the global one, each AI provider its own instance.
- `packages/ai/engine`: the AI engine. `ModelProvider` is the port; `StreamingProvider` holds what every streaming provider shares (post through its client, read server sent events, guard each one, map it), and two providers extend it: `AnthropicProvider` (knowledge cached for an hour with `cache_control`, effort as `output_config`) and `OpenAICompatibleProvider` (OpenAI, Gemini, Groq, OpenRouter, Mistral; effort as `reasoning_effort`, `prompt_cache_key` where taken). Requests and events go through mappers and stream guards. `AiEngine` takes ordered routes per tier, validated by `RouteValidator` when it is made, and answers from the first that works: a refusing route (a bad key, an unknown model) is skipped for the next, a tier falls back to its fallback tiers' untried models, usage is priced per route, and every answer ends with an `EngineReport`. Busy responses (429 with `Retry-After`, 529, 5xx) are retried once with jitter by the provider's client (`MODEL_HTTP_RETRY`), so the engine itself does not retry by default.
- `packages/server/kv` and `packages/server/quota`: `KeyValueStore` with `MemoryStore`, `UpstashStore` (the official client, automatic deserialisation off, pipelined) and `ResilientStore` (falls back to memory for a cooldown when the shared store fails); `SlidingWindowLimiter` and `DailyQuota` on top.
- `packages/ai/ask`: the domain. A body is guarded (`isAskBody`), validated (`AskRequestValidator`) and mapped (`AskRequestMapper`); `PromptMapper` turns it into an engine request with the knowledge first; `AskService` refuses before any model call (the visitor's limit, the shared `AnswerCache`, the limit for everyone, the daily budget), lets one request answer a burst of the same first question while the rest wait, turns engine events into ask events (the `[[sources: ...]]` line split off, em dashes made commas), spends the report's cost, caches answers served at the tier asked, and logs one record per answer. `ASK_ERROR_STATUS` is the one status map for server and client.

`src/services/ask/` is the composition root. `server.ts` takes the shared store (`services/store/server.ts`: Upstash from `KV_REST_API_URL` and `KV_REST_API_TOKEN` from the Marketplace, memory without them, shared with the voyage's board) and builds the limits, the engine and the service; the page must never import it, and loads `client.ts` with a dynamic import on the first question. `routes.ts` turns `ASK_PROVIDERS` in `src/config/ask.ts` into engine routes for the providers that have keys, in `ASK_PROVIDER_ORDER` (Gemini's free tier first at no cost, then Claude Haiku 5.5 and Sonnet 5.5, then OpenAI) unless `ASK_PROVIDERS` in the environment reorders or narrows them. A new provider is a config entry, plus a provider class only if it speaks neither API.

Tokens: the whole site goes in every prompt, because retrieval would cut tokens but drop context and break the cached prefix; caching makes the full prefix cheap instead. `PortfolioKnowledgeMapper` drops lines the site says twice, and a test holds the prompt under `ASK_KNOWLEDGE_TOKEN_BUDGET`. The daily budget is $1 (`ASK_DAILY_BUDGET_USD`), priced from each provider's reported usage; free tier answers cost nothing against it, and the hard monthly caps are the spend limits set with each paid provider. Visitors are counted by a salted hash of their address (`ASK_SALT`). Every answer writes one `ask.answer` JSON line (provider, model, outcome, attempts, time to first token, tokens, cache hit ratio, cost) and the routes are logged once as `ask.routes`.

The rules the agent answers by are in `prompt.ts`. `src/services/ask/evals.ts` holds the evals: a test checks every term they expect is in the knowledge, and `ASK_EVAL_URL=<deployment> npx jest __tests__/src/services/ask/evals.test.ts --watchAll=false` runs them against the real models.

### Accessibility

The site aims for WCAG 2.2 AA, the level EN 301 549 points to. Motion follows one switch: the `motion` setting (system, reduced, full) and the device's reduced motion setting give the root's `data-motion` (`reduced` or `full`), written before the first paint by `motionScript` in the document's head and kept in step by `PreferencesProvider`; every style rule reads it through `media.reducedMotion`, `prefersReducedMotion()` reads it where code acts, and `useReducedMotion` follows it live for what runs on its own (the backdrop, the binary rain, the portraits, the dealer, the typewriter, which then stays on its phrase, and the voyage). The header's `MotionSwitch` (and its row in the phone menu) moves the setting (`toggledMotion`), so the page can be kept still from the page itself (WCAG 2.2.2). As with `COMPACT`, a rule under `media.reducedMotion` is written against the component's shared class, so it never depends on a prop (a data attribute carries a per element difference, as the heatmap's `data-shown` does), it outranks every prop rule on the same property whatever the order (so it never sets what a prop decides, such as a losing duel side's dimming), and a rule with a parent selector nests the still rule inside it (`button:hover & { ${media.reducedMotion} { ... } }`), never the other way round. In the voyage: its keys leave a field being typed in alone but for Escape (`VOYAGE_KEYS`' `skip`); focus that falls to the page's body when a control goes away goes back to the stage, where the keys still reach; the HUD layers (marked `data-hud-layer`) go `inert` under the hangar or a port; the dialog closes through its own `close()` (`closeDialog`), so the browser hands focus back to what opened it; the card that comes up takes focus (the leave question on Stay); its lines are spoken once each, in order, through two regions that stay mounted and keep their last few lines as separate children (`LiveRegion`, polite and urgent), its countdown frames carry no live region of their own, and a line and its fade wait while the run is paused or the hangar is open, then run only the time left; photo mode zooms and looks round by button too (`zoomStep`, `look`; the map scales itself, and in flight a touch screen zooms by pinch only, which the statement lists); the compact bars carry an icon each; and the bright flickers (the supernova, a burst's warning, entry plasma, the decoy flare, a hull breach) stay under two pulses a second (WCAG 2.3.1). The statement is `/accessibility/` (`src/pages/accessibility.tsx`, its words in `src/data/portfolio/accessibility.ts`), linked from the foot of the page and listed in the sitemap; it says only what is true now and lists what is not yet, so it changes when either does.

### Reveals replay

`useInView` has three modes, decided by the tested `nextInView`. It follows whatever element its ref holds after each render, so an element that appears later (a branch rendered only in some views) is still watched. Left at its default it replays: on once `threshold` of the element is on screen, off only once the element has left the screen entirely, so scrolling back to something plays it again and nothing runs backwards while still visible. `once: true` is for one off work such as building a drawing; `once: false` follows the element exactly, for loops that pause off screen. Anything driven by it must reset when it turns off: `useDecodedText` returns to bits, `useAnimationProgress` to 0, the portrait engine rewinds, and duel rounds unplay only when they drop back below the screen.

### Loading flow and dialogs

`Layout` renders `<AppLoader />` over the content, which renders underneath from the start so it is painted and measured by the time the intro lifts; the loader only holds the page still (`useScrollLock`). `AppLoader` flips `isLoading` off after 1s and `isReady` on after 3s, once, from mount, so the intro is time based, not load event based. Canvases still size from a `ResizeObserver`, never a one off read.

Dialogs (the lens chooser, the mobile menu, the terminal's quest dialog, the project region map) are native `<dialog>` elements driven by `useModalDialog(ref, isOpen)`, which calls `showModal()` (focus trapping, Escape and the backdrop for free), holds the page still while open and returns a backdrop click handler. `useScrollLock` counts its holders, so one dialog closing never frees the page while another holds it, and `usePageHeld()` tells work that should pause meanwhile, such as the backdrop. The region and quest dialogs are lazy (`LazyRegionDialog`, `LazyTerminalDialog`): their code loads on first open and they are mounted only while open.

The layout container uses `overflow: clip`, not `hidden`. `hidden` makes it a scroll container and silently breaks `position: sticky` for every section inside it.

### Performance

All scroll reading goes through one shared `ScrollFrame` (`packages/interaction/scroll-frame`, bound to the page by `useScrollFrame` in `src/hooks`): every subscriber reads layout, then every subscriber writes, at most once a frame, from one passive listener. A task's `read` gets `rectOf(id)` with a per frame cache; its `write` should put continuous values (progress) into CSS variables on the element that draws them and only set React state when a discrete answer changes. Never add a `window` scroll listener of its own, and never write variables on `:root`, which restyles the whole document. `__tests__/src/repo/pageBundle.test.ts` walks the home page's static imports and fails if they reach fetchff or the API client: anything that talks to a server loads on first use. For on and off states use `useInView` (IntersectionObserver), which costs nothing while scrolling.

Every canvas effect binds through `useCanvasEngine(canvasRef, { create, resize, sizeRef, isEnabled, nearMargin }, deps)`: it builds the engine once the canvas is near the screen, sizes it from a `ResizeObserver` at the device pixel ratio and again whenever that ratio changes (a move to another screen, a zoom, which no size observer reports), rebuilds on `deps` and stops it on unmount; a rig actor also checks its scale against the canvas's real size every frame, so it never draws at a stale one; starting and stopping while built is the caller's. `create` may be async, and engines that are not needed on first paint import their package inside it (`await import("@/packages/games/bug-raid")`), with only `import type` at the top of the component, so their code stays out of the page bundle. App config that a lazy engine reads must not import that package's values either: Bug Raid takes a partial theme for this reason. Animated components pause off screen (`useInView` with `once: false`), and a frame driven clock (`useAnimationProgress`, with an optional start delay) belongs in the smallest component that shows it.

## Conventions

Enforced by `.eslintrc.json` (typescript-eslint `recommended-requiring-type-checking` + `jsx-a11y` + `styled-components-a11y`):

- Double quotes, semicolons required, `curly` always, `eqeqeq` smart.
- `import/order`: react first → other external → `@/*` internal, blank line between groups, alphabetized case-insensitively.
- Path aliases (`tsconfig.json`): `@/components/*`, `@/pages/*`, `@/layouts/*`, `@/hooks/*`, `@/data/*`, `@/styles/*` map into `src/`, but **`@/types/*` maps to the root-level `types/` directory**, not `src/types`.
- TS `strict: true`; several unsafe-* rules are deliberately off, but `no-floating-promises`/`no-explicit-any` are too, so don't assume they'll catch mistakes.
- Commits follow `feat:` / `fix:` / `chore:` / `docs:` / `refactor:` prefixes. **Do not add `Co-Authored-By` trailers.**
- **Never use em dashes.** Not in site content, code comments, docs, or commit messages. Use a comma, a full stop, or a colon.

- `src/pages/_document.tsx` collects styled-components styles via `ServerStyleSheet` and loads Roboto (which `globals.css` asks for). It replaced a misnamed, malformed `_documents.tsx` whose `enhanceApp` returned a whole `<Html>` tree. That file was never picked up by Next, so before this the app shipped no SSR styles and never loaded its font. Keep the standard `enhanceApp: (App) => (props) => sheet.collectStyles(<App {...props} />)` shape.
- Tests mirror `src/` under `__tests__/src/`: packages and services, pure logic pulled out of components (journey, menu stops, carousel paging, typewriter, History branches, switch effects), shared hooks and components with React Testing Library, and `pages/index.test.tsx`, which renders the whole page in every view inside its providers and fails on a missing section or any `console.error`. Keep logic testable by putting it in a pure function beside the component. Jest compiles through Next's bundled Babel (`__tests__/setups/babelTransform.js` with `.babelrc.js`), so twin.macro runs in tests too; `jest.setup.js` stubs the observers, `matchMedia`, the dialog API and canvas. A test that needs things on screen swaps in its own `IntersectionObserver`. Every file under `__tests__/` counts as a test suite, so shared test data goes in a `fixtures/` folder, which `jest.config.js` ignores.
- tsc never runs twin.macro, so a Tailwind class twin does not support only fails when the file is compiled (a test that imports it, or the build). To check a component directly, compile it with Next's bundled Babel: `require("next/dist/compiled/babel/core").transformFileSync(file, { configFile: "./.babelrc.js" })`. The root `@babel/core` is Jest's older copy and refuses `next/babel`. Twin 2.8 lags Tailwind 3: `border-x-*` and `cursor-crosshair` do not exist, `keyframes` must come from `styled-components`, and underscores inside arbitrary values (`grid-cols-[1fr_2fr]`) are not turned into spaces, so the class is dropped without any error. Put such values in a `css` block.
- This repo is public, so no secret ever goes in it: keys live in Vercel's environment, `.gitignore` ignores every `.env*`, the commit hook warns on a staged env file or anything shaped like a key (`findSecrets` and `isEnvFile` in `scripts/agent/rules.mjs`), and `__tests__/src/repo/secrets.test.ts` fails if any tracked file holds one. No env file is tracked: the switches `DEBUG` and `ANALYZE` default to off in code and are set in the shell when wanted (`ANALYZE=true npm run build`), and an env file ever committed again may hold only those (`SAFE_ENV_NAMES`). Only `DEBUG` is exposed to the client (via `env` in `next.config.js`, read as `process.env.DEBUG === "true"`). The site's address is `SITE_URL` in `src/config/site.ts`, not an environment variable.
- `next.config.js` sets `trailingSlash: true` and strips all `console.*` except `console.error` from production builds.
- An image `quality` must be listed in `images.qualities` in `next.config.js` (55 and 75 now); Next 16 quietly serves the nearest listed one otherwise. Jest does not read that config, so the page test passes it through `ImageConfigContext`.
- Lighthouse reports live in `analyze/*.pdf`.
